# Phase-2 fixes + Phase 3 review — 741d00a / b6fc0d8

Static review only; no cargo or live-service actions. Current crate sources match
b6fc0d8. The phase-2 transaction fix, ordinary identity-collision fix, ordered
timeline reads, durable Telegram retry path and incoming sender authorization
address their original scenarios. The Stop hook now flushes before acknowledging.
The following remaining/new bugs prevent calling all nine findings closed.

- **P1 — crates/orch-mcp/src/main.rs:313** — Inbox acknowledgement still precedes delivery to the MCP client. **Scenario:** orchd commits Ack, then the tool is cancelled, stdout fails, or the MCP process dies before its queued result is written. Retrying returns no messages. **Fix:** move acknowledgement out of `call_tool` into a delivery/receipt protocol; at minimum acknowledge only after successful output flush and retain replayable batches for ambiguous delivery. The cancelled daemon wait is now nondestructive, but this later loss window remains.

- **P1 — crates/orchd/src/telegram.rs:223** — Failed incoming updates are still permanently skipped. **Scenario:** a valid answer encounters a database failure on all three attempts; offset advances anyway and Telegram will not redeliver it. **Fix:** distinguish invalid updates from transient failures; retain unapplied valid updates durably for retry before advancing the offset. Logging the failure is not durable application.

- **P2 — crates/orchd/src/bus.rs:413** — Question retry deduplication works only while the question remains open. **Scenario:** cancel `ask_human` before receiving its ID, Murat answers, then retry the same call: the answered question no longer matches, so another question is created. **Fix:** persist a request/idempotency key across retries and recover the original question regardless of its state; text equality alone cannot distinguish retries from intentional new questions.

- **P1 — crates/orchd/src/server.rs:507** — Nudge safety remains a screen-check race and fails open for unknown states. **Scenario:** the initial idle check succeeds, then the agent opens an unrecognized dialog or exits back to its shell during the 250 ms delay. Only `Blocked` suppresses Enter; `None`, `Done` and unknown herdr status do not. The detector also classifies any unmatched agent screen as Idle. **Fix:** use agent-owned input readiness/delivery rather than negative screen-pattern matching; fail closed on any lost readiness and coordinate delivery with the receiving agent. A status CAS does not reserve the PTY input context.

- **P1 — crates/orchd/src/ui.rs:152** — Spawn and layout insertion are not one atomic operation and lack rollback. **Scenario:** NewTab validates a workspace, another client closes its last pane, then spawning completes and `add_tab` fails. The request reports failure but leaves a running unplaced pane. Split has the same race when its target disappears. **Fix:** reserve/revalidate the layout target under serialized mutation and terminate/remove the newly spawned pane if placement fails.

- **P2 — crates/orch-proto/src/layout.rs:317** — Removing a preceding tab changes the selected tab unexpectedly. **Scenario:** tabs A/B/C, active B (index 1); another client closes A. Clamping index 1 selects C instead of preserving B, so subsequent input targets a different pane. **Fix:** preserve active tab identity or decrement the active index when removing an earlier tab.

- **P1 — crates/orchd/src/ui.rs:333** — Agent/question event payloads can regress state, and lag recovery never restores them. **Scenario:** an ask commits then pauses before emitting; its answer commits/emits first; the delayed open-question event makes the TUI show an answered question as open indefinitely. If an answer event is dropped by broadcast lag, the lag branch fetches only messages and likewise leaves stale questions/statuses. **Fix:** use events as hints for authoritative agent/question reads, with revisions or complete resynchronization after lag.

- **P1 — crates/orch-proto/src/mux.rs:58** — Mux buffering is unbounded at both the transport writer and each channel's incoming queue (lines 134/210). **Scenario:** SSH stops draining while panes keep updating; the proxy keeps draining orchd into heap queues, defeating its backpressure and accumulating obsolete frames until memory exhaustion. **Fix:** bound queued bytes globally and per channel, with flow control or slow-channel closure/resnapshot; do not drop arbitrary protocol byte fragments.

- **P1 — crates/orch-proto/src/mux.rs:131** — Proxy transport EOF/error does not close its channels. **Scenario:** the SSH input ends with active event/attach channels. `serve` returns without clearing `chans`; bridge cleanup closures retain that same map, whose senders keep their incoming receivers alive. Tasks and orchd sockets can remain open, retaining controller ownership. **Fix:** explicit connection-wide teardown on every exit/error: clear senders and cancel/join bridge tasks, including in-progress connects and blocked writes.

- **P1 — crates/orch/src/tui.rs:808** — Pane/tab switches do not establish an input-routing barrier. **Scenario:** receive Ctrl-b l followed immediately by command text, especially over SSH. Focus is requested asynchronously, while `send_input` still resolves the old session focus; text goes to the old pane. Ctrl-b n/number has the same problem. **Fix:** serialize switch completion with subsequent input, or update a validated local target immediately and queue input until its attach is ready.

- **P2 — crates/orch/src/tui.rs:559** — Unexpected attach-stream closure silently leaves a dead cached view. **Scenario:** a pane connection closes without `Stream::Exit` while the event connection stays healthy. The task returns, but `views` still contains the pane; `sync_views` never reopens it and input send failures are ignored. **Fix:** report every unexpected stream/write failure, remove or mark the matching attachment generation, and reconnect with a full snapshot.

- **P1 — crates/orch/src/tui.rs:781** — Overlays do not recognize bracketed-paste boundaries. **Scenario:** paste a multiline answer while the focused shell has enabled bracketed paste. The start marker is ignored, the first newline submits the answer and returns to Normal, and the remaining pasted text/newlines are forwarded into the shell/agent pane. **Fix:** parse paste as a distinct input event, keep its entire payload in the selected overlay, and require a separate explicit submission.

- **P2 — crates/orch/src/tui.rs:759** — Key parsing assumes every stdin read ends on a key boundary. **Scenario:** an overlay receives ESC and `[A` in separate reads: ESC closes it, then `[A` is typed into the pane. Split UTF-8 is silently discarded by `edit_line`. **Fix:** retain incomplete CSI/SS3/UTF-8 sequences across reads, with an Escape timeout, or use a streaming terminal-input decoder.
