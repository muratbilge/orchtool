# Phase 2 review — 2e7f901

Static review; no cargo, live services, messages or configuration changes. The
reviewed crate sources in the current checkout match 2e7f901.

- **P1 — crates/orchd/src/bus.rs:261** — Inbox messages are consumed before delivery, including by cancelled waits. **Scenario:** cancel an MCP `read_inbox(wait_seconds=30)`; MCP drops its socket, but `server.rs:329` keeps awaiting `inbox_wait`. A message arriving afterward is marked read, then the reply fails on the closed socket; the next inbox call sees nothing. The Stop hook also loses its consumed batch if its subsequent status request fails/times out before printing (`crates/orch/src/bus.rs:299`). **Fix:** cancel waits on disconnect and use explicit acknowledgement/durable delivery receipts rather than marking read before successful consumption. Disconnect cancellation alone does not close the delivery race.

- **P1 — crates/orchd/src/bus.rs:388** — Answer state and answer-message insertion are separate commits. **Scenario:** crash, or an insertion error, after updating the question but before `self.send` at line 397. The question is answered, yet its inbox answer never exists; retry returns `won=false` and cannot repair delivery. `ask` similarly commits the question before its timeline/inbox row. **Fix:** transactionally persist each question transition and corresponding message, then notify after commit.

- **P1 — crates/orchd/src/bus.rs:135** — Registration can merge unrelated agents and their inboxes. **Scenario:** two same-kind agents in the same cwd outside a recognized pane both have `pane=None`; `None == None` reuses the same name, so either can consume the other's messages. A six-hour-old entry is also reassigned even if its agent is still running. Additionally, persisted `orch:p1` associations survive daemon restart while pane numbering restarts at p1, so the earlier lookup at line 104 can assign a new agent the previous session's identity. **Fix:** use a stable agent/session identifier and daemon-generation-qualified pane IDs; do not infer identity from missing panes or elapsed time, or silently transfer mailboxes.

- **P2 — crates/orchd/src/bus.rs:238** — Message events can arrive out of database order. **Scenario:** sender A commits ID 10 and is descheduled after unlocking; B commits/emits 11, then A emits 10. `follow_log` advances `last` to 11 and discards 10 (`server.rs:375`), permanently omitting it from the live timeline. **Fix:** serialize publication with commit order, or treat notifications as hints and drain ordered database rows after the last delivered ID.

- **P1 — crates/orchd/src/telegram.rs:204** — Incoming offsets are persisted before handling the update. **Scenario:** after saving the next offset, the daemon crashes or `bus.answer`/`bus.send` fails. On restart Telegram polling skips Murat's unapplied reply. **Fix:** commit update-ID deduplication, the bus mutation and checkpoint together; advance only after successful durable application. Moving the checkpoint afterward without deduplication would instead duplicate ordinary message replies on retry.

- **P1 — crates/orchd/src/telegram.rs:169** — Outgoing delivery relies solely on transient broadcast events. **Scenario:** a question arrives during a network outage; `forward` errors once and the event is discarded. Restart, subscription lag, or asking before pairing also leaves persisted questions/messages unsent with no automatic retry. **Fix:** maintain a durable outgoing queue/cursor, reconcile pending records on startup/pairing, and retry failed deliveries; `/open` is only manual recovery for questions.

- **P1 — crates/orchd/src/telegram.rs:273** — `TG_CHAT` bypasses the private-chat restriction, and answer authorization checks only chat ID. **Scenario:** configure a group ID through the supported environment/file path; any member of that group can click an answer button or reply as Murat because neither callback nor message handling verifies the sender. **Fix:** enforce private-chat configuration and incoming chat type, and bind authorization to the paired user's ID as well as the chat for both update types.

- **P2 — crates/orch-mcp/src/main.rs:320** — A newly created question's recovery ID is withheld until the wait finishes. **Scenario:** cancel `ask_human` after creation but before its result. The task aborts, the question remains open, and the caller has no ID for `wait_for_answer`; retrying `ask_human` creates a duplicate. Existing restart coverage uses `wait_seconds=0`, which avoids this window. **Fix:** make creation idempotent with a recoverable client key and expose pending-question recovery, or return the durable ID before beginning a separately resumable wait.

- **P1 — crates/orchd/src/server.rs:413** — The idle check does not authorize later terminal input. **Scenario:** after the nudger reads `idle`, a prompt/hook sets the agent to working or blocked; the nudger overwrites that newer status and types anyway. There is another 250 ms window before its unconditional Enter. A stale idle record after the agent exits can instead send the notice to its shell. **Fix:** deliver through the inbox/hook or an agent-owned readiness handshake; an earlier status snapshot cannot safely authorize raw PTY text and Enter. At minimum, never overwrite newer status and never send Enter after failed text admission.
