# Phase 1 review — 30dd490

Static review only; no cargo or live-daemon tests. Reviewed files match 30dd490
in the current checkout. Dependency behavior checked against installed sources.

- **P1 — crates/orchd/src/render.rs:86** — Mouse modes are never reliably disabled. `input_mode_formatted()` encodes against default modes; vt100 emits nothing for mouse None/default encoding, rather than resetting previously enabled modes. **Scenario:** vim enables mouse + SGR, then disables them on exit; the attached terminal keeps sending mouse escapes to the shell. Full snapshots also fail to reset this state. **Fix:** track previous modes and emit transitions; explicitly reset mouse modes/encodings before full snapshots. Also reset `?9l` in `attach.rs:41` on detach (currently omitted).

- **P1 — crates/orchd/src/render.rs:75** — Clipping counts source cells but can emit a complete wide glyph crossing the view boundary. vt100's row formatter emits a wide cell's text even when its continuation lies outside `w`. **Scenario:** a 40-column pane has `界` starting at column 20; a 20-column observer receives that glyph at its last column. It wraps into the next row; on the bottom row it can scroll the whole display. The cached rows then prevent repairing unchanged rows. **Fix:** replace a partially clipped wide glyph with a styled blank; add right-edge and bottom-right observer tests.

- **P1 — crates/orchd/src/server.rs:290** — Controller changes can be lost before the watch receiver is subscribed. **Scenario:** A becomes controller, then waits sending its attach reply; B takes over before A calls `subscribe_controller()`. A subscribes with B already the current value, so `changed()` does not announce the demotion. A's CLI keeps believing it controls the pane although its input is discarded. **Fix:** subscribe before registration and reconcile the current controller value before the reply and loop, rather than depending only on future changes.

- **P1 — crates/orchd/src/pane.rs:169** — PTY size, parser size and generation are updated separately. **Scenario:** concurrent resizes interleave as A's PTY ioctl, B's ioctl/parser update, A's parser update: the PTY retains B's size while the parser retains A's, corrupting wrapping indefinitely. Even one resize lets the reader parse a SIGWINCH redraw between the ioctl and parser update. **Fix:** serialize resize operations with terminal parsing/rendering, updating size and generation under the same lock; revalidate controller ownership when applying its size.

- **P1 — crates/orchd/src/server.rs:94** — Kill reports success and forgets panes that remain alive. `Pane::kill()` uses portable-pty 0.9.0's cloned killer, which sends only SIGHUP to the child PID. **Scenario:** `sh -c 'trap "" HUP; while :; do sleep 1; done'` ignores it; after the timeout the map entry disappears while the process and reader/writer threads remain alive and unreachable. **Fix:** check termination, escalate to a hard kill with an explicit process-group policy, and retain/report the pane if termination fails; clean up reader/writer ownership too.

- **P1 — crates/orchd/src/pane.rs:85** — PTY input buffering is unbounded. **Scenario:** a pane stops reading stdin; its writer blocks in `write_all`, but repeated sends/pastes continue allocating queued vectors until orchd exhausts memory. Terminal query replies use the same queue. **Fix:** enforce a byte budget with nonblocking admission/error or async backpressure; do not block Tokio workers or the terminal reader on a bounded synchronous send.

- **P2 — crates/orchd/src/pane.rs:152** — Sleeping 50 ms does not establish that final output was parsed. **Scenario:** the reader is delayed by scheduling or a held terminal lock after child exit; attach sends its final frame and Exit before that reader processes the tail, so the client permanently misses output. **Fix:** explicitly coordinate child exit and reader EOF/drain completion before sending Exit; define a bounded policy for descendants that retain the slave PTY.

- **P2 — crates/orch/src/attach.rs:30** — Raw terminal setup can fail before a restoration guard exists. **Scenario:** raw mode succeeds but stdout write/flush fails (for example, stdout is redirected to `/dev/full`); `?` returns before constructing `RawGuard`, leaving stdin's terminal raw. **Fix:** construct the guard immediately after enabling raw mode so subsequent setup failures run its destructor.
